# MemArk 文档最终评审

评审范围：`docs/a.md` ~ `docs/f.md`

评审方法：对三份候选评审交叉核对，并回到原始文档逐条复核。本文只保留已被原文直接支撑的问题；对缺乏证据、带有较强推测色彩或已被原文反证的结论，不纳入最终问题清单。

## 结论

当前这组文档不适合直接作为可执行安装文档合并。主要问题不是“表述还可以润色”，而是存在多处会让用户或 AI 助手在主路径上直接失败的阻断项：引用了仓库内不存在的文件、依赖未验证且文中已明确承认是假设的命令接口、以及多套互不兼容的架构文档并存却没有权威版本说明。

建议结论：**Request Changes**

## 已确认问题

### 1. 快速开始引用了仓库中不存在的关键文件，主流程会直接中断

证据：
- [docs/c.md:15](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/c.md#L15) 要求“把本目录下的 `skill.md` 交给 AI 助手”
- [docs/f.md:66](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/f.md#L66) 也要求“将本目录下的 `skill.md` 交给 AI 助手”
- [docs/c.md:49](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/c.md#L49) 要求下载 `memark.py`
- [docs/f.md:83](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/f.md#L83) 同样要求下载 `memark.py`

复核结果：
- 当前仓库只有 `docs/a.md` 到 `docs/f.md` 以及三份评审文件，没有独立的 `skill.md`
- 当前仓库也没有可直接下载的 `memark.py`

影响：
- 用户按照 README / 快速开始执行时，会在第一步或前几步就找不到文件
- 这不是“体验不佳”，而是安装链路被阻断

建议：
- 明确提供唯一的正式 `skill.md` 和 `memark.py`

### 2. 核心流程依赖未验证的占位命令，文档自身已承认接口是假设

证据：
- [docs/e.md:122](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/e.md#L122) 明确写明“这里假设有一个命令 `mempalace list-rooms --since <timestamp>`”
- [docs/e.md:227](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/e.md#L227) 明确写明“假设 graphify 提供了 build 命令”
- [docs/e.md:280](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/e.md#L280) 明确写明“假设 mempalace 提供 get-room 命令”

建议：

### 3. 理念层与实现层的关系没有讲清，文档版本口径混杂，缺少权威版本说明

证据：
- [docs/c.md:3](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/c.md#L3) 使用的是 `MemPalace + LLM Wiki` 表述
- [docs/f.md:3](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/f.md#L3) 使用的是 `MemPalace + Graphify` 表述，且正文将 Graphify 说明为 “LLM Wiki 的落地实现”
- [docs/c.md:47](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/c.md#L47) 使用 `llm_wiki/{raw,wiki}`
- [docs/e.md:56](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/e.md#L56) 使用 `graphify_data/{raw,vault}`
- [docs/c.md:131](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/c.md#L131) 命令写为 `memark serve --mcp`

复核结果：
- `Graphify` 可以被理解为 `LLM Wiki` 理念的具体实现版本，这两者并非天然冲突
- 当前问题不在于“概念互斥”，而在于文档没有把“理念”和“实现”的关系、以及不同版本文档的适用范围讲清楚

影响：
- 读者仍然无法判断当前应当遵循哪套目录结构、命令接口和安装说明
- 即使作者意图是“从理念走向实现”，如果历史文档和正式文档并存且没有边界说明，最终效果仍然是误导

建议：

- 其余版本要么删除，要么明确标成历史草稿、方案演进记录

### 4. `docs/a.md` 的配置读取未展开 `~`，会导致部分路径按字面值使用

证据：
- [docs/a.md:75](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/a.md#L75) 到 [docs/a.md:83](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/a.md#L83) 在 YAML 中写入了多处 `~/memark/...`
- [docs/a.md:114](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/a.md#L114) 使用 `yaml.safe_load(...)` 直接读入配置
- 在 [docs/a.md:141](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/a.md#L141)、[docs/a.md:176](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/a.md#L176) 等处，路径又直接来自 `config['paths'][...]`，未见统一 `expanduser()`

影响：
- 在 Python 中，YAML 里的 `~` 不会像 shell 一样自动展开为用户目录
- `a.md` 这版脚本中的部分文件操作可能直接使用字面字符串 `~/...`

建议：
- 在配置加载后统一对路径项做 `Path(...).expanduser()`
- 或在每一处消费配置路径时显式展开

### 5. 部分定时任务示例会覆盖用户现有 crontab

证据：
- [docs/d.md:122](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/d.md#L122) 使用 `echo "..." | crontab -`
- [docs/f.md:112](/Users/zhaoyu/Downloads/code/my-memark/memark/docs/f.md#L112) 同样使用 `echo "..." | crontab -`

影响：
- 这种写法会直接用单条任务替换整个 crontab
- 用户已有的定时任务可能被清空

建议：
- 使用 `(crontab -l 2>/dev/null; echo "...") | crontab -` 之类的追加方式
- 更稳妥的做法是先去重，再追加，并明确提醒用户这是会修改系统定时任务的步骤

## 修订优先级

建议按以下顺序处理：

1. 先修正文档引用，保证仓库内文件名、下载路径、入口脚本都真实存在
2. 再删除或归档旧方案，只保留一套权威文档
3. 然后补齐并验证所有外部依赖接口，避免“假设命令”出现在主路径
4. 最后处理 `~` 路径展开、crontab 写法、错误处理和可维护性细节

## 最终判断

这批文档当前最大的问题是“不能稳定指导安装”，而不是“写得还不够漂亮”。在正式合并前，至少应修复上述 1-5 项中的前 3 项，否则用户和 AI 助手都会在主流程中遇到高概率失败。
